## Field 5. Commands

The batching process manager is a long-running durable PM (O2), one instance per `(tenant, program)` pool, REUSING the Decision 77 engine wholesale (the `@andpay/engine` `SagaEngine` + `setTimer`/`claimAndFireDueTimers`, FOR UPDATE SKIP LOCKED with leases, O4-isolated), no new engine, driven by a fulfillment-pinned client over the fulfillment-schema saga tables (ratified). It advances by consuming `fct.tms.assignment.v1` (pool accrual) and durable timers (the daily configurable-time evaluation and the max-wait age check), and on trigger it creates the `batch` row and emits `fct.fulfillment.batch.v1` in ONE transaction with its own outbox (E1). The batch-born signal is a FACT, not a command; Fulfillment emits no command to another context (C5, O1). The `cmd.fulfillment.*` dispatch-lifecycle command topics (composition, package) are spec 08's intra-context engine steps and are NOT produced here. Manual-trigger and record-hold are audited class-3 operations (S13, actor-on-behalf to the 6e store): MANUAL creates a Batch below lot size, HOLD moves a `pending_pool_entry` to HELD (excluded from triggers) until released. In v1 these are invoked directly or by fixture (the ops portal wires them at step 9, the spec-06 TMS-amend precedent), and the actor is recorded on `batch.triggered_by_actor`; the tamper-evident 6e store write is deferred to the step-9 portal edge (C4: fulfillment cannot write Auth's store). Lot-size and max-wait are Fulfillment DOMAIN config (admin-editable, audit-logged old/new per BRD), config-as-code and CODEOWNERS-gated, NOT a runtime control plane (S23).

## Field 6. Ports and adapters

The C6 Fulfillment File Ingest port (103a), file-shaped not webhook or command (the 06.D4 file-vs-command line, T11: no vendor schema inland). This spec implements ONE inbound adapter: the manufacturer intake sheet (CWD), which is the ONLY Unit-creating channel (103d). The sheet is S8-untrusted (103b): accepted ONLY from the authenticated class-6 vendor principal (spec 04), integrity and schema verified before any state change; an unverifiable or schema-invalid sheet is rejected whole. In v1 the ingest receives an already-resolved class-6 `LeanClaim` and runs the secret-free `authorize(claim, 'sheet:submit-intake', { vndrId, workQueue }, cfg)` two-gate from `@andpay/authz` (ratified; raw `apsk_` resolution is the step-9 edge's job, S14). Posting is PARTIAL-FILE with discrepancy quarantine (103d): valid rows create Units, malformed or ambiguous rows route to a Fulfillment exception state plus an ops case, never an auto-guess. The adapter maps the vendor sheet to the internal Unit contract; the vendor's column shape never travels inland (T11). The print/ship return sheet adapter and the real-time shipping-partner channel are spec 08 and step 8 respectively, the same port, different adapters. Completeness is reconciled against manufacturer records under M8 discipline (no money, same posture).

## Field 10. Idempotency (06.A grammar, E6 inbox, no M7 floor)

* Demand-fact consumption: dedup on the envelope `dedup_key`; the `pending_pool_entry` upsert is idempotent on `asgn_` UNIQUE (re-delivery is a no-op, pool count stable).
* Manufacturer intake sheet: file-level `{vendor}|{file_id}` (103c) via the inbox; per-Unit birth `{device_serial}|intake` for serialized (the `device_serial` UNIQUE also bites), `{vendor}|{file_id}|{product_type}` for a quantity-line load.
* Batching PM: each `saga_step` idempotent on its 06.A-derived key (spec 03); durable timers fire at-least-once with an idempotent effect; a trigger evaluation is idempotent on `{tenant}|{program}|{trigger_epoch}` so a re-fired timer does not double-create a Batch.
* Batch fan-out to Units: `{btch_}|unit|{k}` (06.A rule 2) for the allocation link.
