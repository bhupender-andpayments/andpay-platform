# AndPayments Architecture, Rules, Guardrails & Risk Register

> **Purpose.** This is the enforcement layer for `architure_context.md`. `architure_context.md` records _what_ was decided and _why_, with history. This file is the set of rules any new product, service, or change must satisfy, the known traps to avoid, the risks being tracked, and the gate to run before adding anything. Use it as a design-review checklist. If a proposal violates a Tier-1 invariant, it is wrong by default, reconcile or escalate before proceeding.
>
> **How to use it with the model.** At the start of a design session, this file, `architure_context.md`, all chapter files (04, 05, 06, 07), `00_intake_and_build_protocol.md`, and `platform_build_state.md` should be in context. When proposing or reviewing any design, check it against the invariants (Section 1) and run the new-component gate (Section 5). Any violation must be flagged explicitly, not silently worked around.
>
> **Rule IDs** (M=money, I=identity, K=KYC, C=coupling, E=events, O=orchestration/saga, S=security, T=trap) are stable handles so reviews can cite them.

## 1. Inviolable invariants (Tier 1, never break these)

### Money

- **M1.** Ledger is double-entry. Every transaction is balanced, debits equal credits per currency, enforced at write. A half-posted or unbalanced transaction cannot exist.
- **M2.** Ledger is append-only. Postings are never updated or deleted. A correction is a new reversing transaction.
- **M3.** Amounts are integer minor units (`bigint`), currency on every monetary row. Never sum across currencies. Resolve the decimal exponent from the currency code, never hardcode "/100".
- **M4.** Only the ledger posting API writes money facts. No context writes ledger tables directly, ever. Posting is a permissioned capability that enforces balanced plus idempotent on every call regardless of caller.
- **M5.** Bank-sponsored Programs post NOTHING to the transaction ledger (zero merchant-fund movement). The fee billed to the bank is a corporate-GL / accounts-receivable matter, handled offline today, kept out of the transaction ledger (the Stripe ledger-vs-billing split). The Program decides which postings exist. Never record money you neither hold nor are owed, and never conflate processing-money with billing-revenue. (Merchant Receivable, when it exists, is an ASSET, not a liability, see `architure_context.md` Section 9 Q2.)
- **M6.** A cross-currency transaction is Model B only (explicit conversion through an FX account, each transaction single-currency and self-balancing). Model A (mixed-currency entries balanced after a rate) is banned.
- **M7.** Every money-mutating endpoint REQUIRES an idempotency key (not optional). Every downstream money-effect key is DETERMINISTICALLY derived from its stable trigger (the client key, or the source event id), never random-per-attempt, so retries collide at the ledger's unique constraint. That unique constraint is the PERMANENT floor: money cannot double-post even if every upper-layer dedup fails. Upper-layer key stores may expire. Same-key-different-payload is rejected; an in-flight concurrent retry is guarded (return 409, never a second execution). The full derivation chain is client key to saga instance id to ledger transaction key to event dedup key (see `architure_context.md` Section 12.6). Derived keys are deterministic structured strings in unique-constrained columns, never UUIDs; entity IDs stay UUIDv7. Implementation at scale (decision 74): the floor lives in a dedicated posting_keys table hash-partitioned BY KEY (a true global unique constraint), inserted in the same transaction as the journal row; journal tables may time-partition and archive, keys are never dropped; a time-partitioned unique constraint is NOT a floor (T13). Key composition follows the canonical grammar (chapter 06.A): {Kc}|{flow} for the instance, {parent_aggregate_id}|{child_qualifier} for spawned children, {aggregate_id}|{step}[|{seq}] for internal steps with seq assigned under the aggregate row lock, {source_event_id}|{purpose} for event-driven postings. Kc never appears below the instance key. The merchant input to key SCOPING derives from the AUTHENTICATED principal (S14, Step 7 Decision 5e), never from a request-body field; a body-supplied merchant_id would open a cross-merchant replay class.
- **M8.** Any money operation whose outcome can be externally indeterminate (a timed-out push payment, a payout with no immediate confirmation, a switch call that does not return) is resolved by authoritative reconciliation against the source of truth, never by assuming success or failure. A wrong assumption is a double-pay or a lost payment. (Applies to money-flow archetypes 2 and 4 and the inbound settlement leg, see chapter 04.)
- **M9.** A posting whose entries depend on a current balance (for example the chargeback split: Merchant Payable to zero, remainder to Merchant Receivable) computes the split by READING the balance and WRITING the balanced transaction inside ONE ledger transaction whose correctness is LOCK-BASED, never isolation-level-based (Decision 113): the involved balance rows are acquired FOR UPDATE before or during the read (multiple rows in deterministic account-id order to avoid deadlock), or the split is computed inside the locking UPDATE via RETURNING, so the read-then-write serializes against every M10 writer regardless of isolation level. Postgres SERIALIZABLE (SSI) alone is INSUFFICIENT here because its guarantees hold only among serializable transactions and ordinary postings run read-committed (decision 75). Never from a stale unlocked read, never split across two transactions. Safe because the ledger is the single strongly-consistent synchronous writer (Section 9; chapter 05). The refund insufficient-Payable split and the cycle Receivable recovery (min of balances) lock their one or two balance rows as above; the escrow sweep is the AGGREGATE-READ variant (a population sum cannot be row-locked) and follows the Decision 113 sweep mechanism specified in chapter 06.D5 (single-statement snapshot recomputed inside the posting transaction, explicit safety margin, low-activity scheduling, the M10 floor as the hard backstop, daily M8 adequacy verification). All three are explicitly in M9 scope (chapter 06.C, 06.D3, 06.D5).
- **M10.** Floor-enforced accounts (Escrow Cash, per-merchant Merchant Payable, wallet/PPI and payroll floats) reject any posting that would drive their balance negative, checked under the account row lock in the same statement as the synchronous balance update. A legitimate negative-Payable situation is expressed only through the explicit M9 split into Merchant Receivable, never a silently negative balance. Unfloored high-volume aggregates (Network Receivable, Fee Revenue, GST Payable) carry NO synchronous balance row; entries are the truth, balances derived. Serializable / read-then-write scope is narrowed to M9 postings and floor updates; ordinary balanced postings run read-committed on the key floor. (Decision 75.)
- **M11.** A ledger transaction TYPE that moves a segregated fund pool (PA escrow, payroll escrow, PPI float, and any S2-aware segregated-pool type) appears in AT MOST ONE M4 holder's allowed-type set (Step 7 Decision 4b/4d). Two holders able to post the same segregated-pool type would enforce that pool's segregation boundary in two places and drift (a T12-class dual-enforcement that breaks S2). Enforced as a GLOBAL validation on the M4 allowlist in CI whenever it changes, never a per-entry check. Non-segregated types (unfloored aggregates such as Fee Revenue, Network Receivable) may have multiple posters without violating this. Corollary of M4 and S2; depends on the type structural binding in S11.

### Identity

- **I1.** One canonical `merchant_id` per legal entity (deduped on PAN/GSTIN). One `customer_id` per consumer. Two tables, optionally linked by a person record, never merged into one "user" table.
- **I2.** ID generation is a local in-process library call. Never a network round-trip, never a central ID service, never a DB sequence round-trip.
- **I3.** Every ID is a typed prefix plus Crockford Base32 of a UUIDv7. The prefix is retained system-wide (never stripped internally). Stored as a native Postgres `uuid` only; the typed string is the wire format on every API, event, log, and service-to-service call.
- **I4.** IDs are immutable, opaque, non-sequential, never reused.
- **I5.** Tenancy/sponsorship attaches to the Program/enrollment, never to the merchant, and never to `parent_merchant_id` (which is reserved for genuine merchant-to-merchant trees only). A bank is a counterparty plus a portal access-tenant, never a merchant.

### KYC

- **K1.** KYC is a provenance-bearing verification record (subject, who verified, regime/level, evidence, status, expiry), never a boolean.
- **K2.** Never copy KYC, always reference it. One record, many references, status changes propagate by event. A local mutable copy is a compliance incident waiting to happen.
- **K3.** Attestation authority is the owning tenant only, non-delegable. The platform operator (super-admin) can capture/upload for anyone but can never attest. In direct Programs, AndPayments holds operator and tenant as two distinct logged roles; attestation is logged as the tenant role.
- **K4.** Reuse is computed (reused / refresh-expired / net-new), gated by sufficiency and validity. Automatic within a Program, consent-gated across Programs.

### Coupling (the rules that keep it "on rails")

- **C1.** Dependencies point downward only: Products to Movement to Ledger. Never upward.
- **C2.** Products never call products. A product needing payment creates a PaymentIntent and lets routing pick the instrument. No sideways product-to-product calls.
- **C3.** Cross-context facts travel as asynchronous events. Synchronous calls only in the money/auth hot path. The test: "do I need the result to continue this operation right now?"
- **C4.** Each context owns its data. No shared database, no cross-context table reads. Data is exposed only through a context's API or its events.
- **C5.** Events are facts ("X happened"), never commands ("do X"). The emitter never knows its consumers. (Commands exist as a separate message class for saga orchestration only, see E7, and never product-to-product.)
- **C6.** All external payment execution goes through the internal Processor Port (a stable interface in AndPayments' own domain terms and IDs: `authorize`, `capture`, `void`, `refund`, `status_check`, `payout_initiate`, `payout_status`, `mandate_setup`, `beneficiary_validate`; the list is REPRESENTATIVE, not exhaustive, per Decision 113, and any new external EXECUTION operation extends the Port under the chapter 06.D4 test: command-shaped calls are Port operations, counterparty truth-at-rest files are ingest contracts). Processors are swappable adapters selected by Routing. No flow, ledger posting, or idempotency key ever depends on which processor served the call. PSP today, own NPCI switch later is a new adapter plus a new route, nothing else changes. Build the Port and one adapter now; do not over-build multi-processor routing before a second processor exists. The issuing side mirrors this as the **Issuing Inbound Port** (chapter 06.E): the network or issuer-processor calls us through a port, never a vendor-schema binding. Settlement files flow through the separate **Settlement File Ingest** contract (chapter 06.D4), one adapter per counterparty; files are not the Processor Port.

### Events and consistency

- **E1.** Every state-owning context has its own outbox in its own database. The state change and its event commit atomically in one local transaction. No central event-publishing service. (This includes a saga orchestrator's command emission, see O1/E7.)
- **E2.** Delivery is at-least-once. Every consumer is idempotent (dedup on the event key). Effectively-once is the target; exactly-once is not pursued.
- **E3.** Every event has a versioned schema in the registry. Backward-compatible evolution only (add optional fields, never remove/repurpose/retype). A breaking change is a new version, both emitted during migration.
- **E4.** Every event carries the standard envelope (id, type, version, timestamp, subject/aggregate id, dedup key, trace id) and a fat-enough payload for event-carried state transfer. Fat-enough never includes PII on money/transactional topics; identity attributes travel on compacted identity topics only (S7, decision 73).
- **E5.** Ordering is per-aggregate. Partition key is chosen per event type by its ordering boundary (payment lifecycle = `payment_intent_id` / `pi_`, the PaymentIntent not the Charge `pay_`; merchant identity = `merchant_id`; account postings = `account_id`). No global ordering key. Ordering is required only within an aggregate, never across (cross-aggregate global ordering is a design smell). Consumers enforce valid state transitions on top of partition ordering, never assume order from keying alone.
- **E6.** Effectively-once is per-effect, never a cross-service transaction. A money posting dedups via the ledger's derived unique key (no separate inbox row). A non-ledger local effect uses the consumer INBOX: dedup-key insert and effect-apply in ONE local transaction (the consumer-side mirror of the outbox). An external side effect (email, third-party PSP) is made idempotent at the provider or tolerates a rare duplicate. When one consumer has two effects across two databases (e.g. a posting plus a projection update), make each independently idempotent; the partial failure across them is the saga's job, never a distributed transaction.
- **E7.** Commands are a separate message class from facts: dedicated command topics, point-to-point, used ONLY by a flow's orchestrator to that flow's own participants. The fact bus carries facts only. An orchestrator emits commands but advances by consuming facts. Commands are never product-to-product (that remains C2). One MSK backbone carries both classes on separate topics; no second broker. Production topology: facts on `fct.<domain>.<aggregate>.v<n>`, commands on `cmd.<participant>.<action>.v<n>`, per-consumer retry/DLQ topics, all schemas versioned. The bus is never request-reply; synchronous hot-path steps are direct calls.
- **E8.** When a producer or flow evolves, keep emitting the facts that existing consumers depend on until they have migrated. Never break the consume-side to serve the create-side. (Stripe layered a Charge per PaymentIntent attempt so analytics and reporting integrations kept working. This is E3 in practice.)
- **E9.** Topic retention and rebuild: transactional fact topics have bounded retention (default 30 days, sized to the projection-rebuild window); identity fact topics are log-compacted keyed by subject id. Every fact-producing context exposes an OWNER BACKFILL CONTRACT, a bulk re-emission path (paginated read API or request-driven backfill stream) of snapshot-grade events in the same schema and envelope, flagged backfill=true. Rebuilds go through the owner's contract, never its tables (C4). Infinite bus replay is not a promise anywhere. (Decision 73.)

### Orchestration and sagas

- **O1.** Money flows are orchestrated, never choreographed. Orchestration is owned PER FLOW by the context that owns it (Money Movement: auth to capture; Settlement: settle to payout). No central or god orchestrator (see T4). Choreography is allowed only for loose downstream fact reactions (notification, analytics, AML).
- **O2.** Short flows (auth to capture, seconds) use a lightweight saga. Long flows (settle to payout, disputes, retry-over-days) use a process manager with persisted state and durable timers. An in-memory saga must never model a multi-day flow. "Hold a command and retry later" is a durable-timer feature of the process manager, never a broker feature.
- **O3.** Compensation in a money flow is a forward reversing transaction (M2), emitted as a compensating command, posted through the same ledger API. Never a DB rollback of a committed posting. Non-money steps compensate per their own semantics.
- **O4.** The orchestration engine is built now (not Temporal), but as an ISOLATED layer with an explicit step + compensation abstraction and command/fact I/O. Saga logic is never smeared into business-service code. This isolation is the condition that keeps a future engine swap (e.g. Temporal) mechanical rather than a rewrite.
- **O5.** Separate intent-level state from attempt-level state. A failed or declined step is terminal for the ATTEMPT (`pay_`); the PaymentIntent (`pi_`) returns to a retryable awaiting-instrument state and is terminal only at completed, canceled, or expired. One intent carries many attempts (aligns with the `pi_` aggregate, E5). Do not model a money flow with a single flat terminal-on-first-failure state.

## 2. Security and compliance constraints (Tier 1, currently UNDER-DESIGNED)

S1 to S5 were flagged as gaps: they are **binding now** even though their detailed design is pending; any product touching cards, funds, or PII must satisfy them, and each must be fully designed before the relevant product ships. Status on each of S1-S5 is **CONSTRAINT NOTED, DETAILED DESIGN PENDING**. S6 to S8 were DESIGNED (chapter 07 and decision 76) and are equally binding. S9 to S24 are DESIGNED (decision 78, Step 7 Decisions 3 to 6, the sandbox, webhook, notification, analytics/reporting, and Fulfillment rails, Step 8 operations, and the AI service rail) and binding.

- **S1. Card data.** Raw card data (PAN, CVV, track data) is never stored, logged, or placed on the event bus. Card data is tokenized; a dedicated card vault holds it; PCI DSS scope is minimized to the smallest possible set of services. RBI card-on-file tokenization applies to the Cards and Acceptance contexts. A PaymentMethod (`pm_`) references the vaulted token, never the raw PAN.
- **S2. Fund segregation.** PA escrow funds, PPI float, and lending capital are never co-mingled. The ledger's separate accounts must enforce this and reconciliation must be able to prove it. (This is the reason Merchant Receivable is an explicit asset account, M5, not a buried negative liability.)
- **S3. Data residency.** Payment data is stored in India (RBI data localization). The regional-partitioning design (Step 6) must honor this.
- **S4. Secrets and keys.** Credentials, secrets, and keys never appear in code, logs, events, or IDs. Encryption in transit and at rest. Key management is a named service (Step 7/8).
- **S5. PII minimization.** Contexts hold only the identity fields they need, as projections, never the full KYC record copied locally (see K2).
- **S6. Residency (DESIGNED, chapter 07.D-E).** Payment data stored only in India: primary ap-south-1, DR ap-south-2 (a DR copy is storage, so DR stays in India), backups/warehouse/search/log archives India-only, replication allowlists enforced as policy-as-code in CI. Foreign support access is access-not-storage, gated and logged. The residency domain is a Program attribute. (RBI 2018 localisation circular plus 2019 FAQ; verify current text at compliance.)
- **S7. PII and erasure (DESIGNED, chapter 07.G).** The ledger and all money events carry IDs only, never PII. Identity attributes travel only on compacted identity topics; erasure = redacted final record plus tombstone. Legal retention (PMLA/RBI KYC) overrides erasure where mandated. Crypto-shredding is the recorded alternative if a long-retention PII topic is ever required. (Decision 73.)
- **S8. Inbound trust (DESIGNED, decision 76).** Inbound notifications, webhooks, and files are untrusted input: signature-verified always; cash-account postings derive only from authenticated bank/PSP sources; duplicates collide on rail-handle keys; recon (M8) is the assurance loop.
- **S9. Fraud-rail degradation posture (DESIGNED, decision 78).** On a fraud-engine latency-budget breach in the auth path: FAIL-CLOSED for every solvency/balance/funds/hard-limit check and for the ENTIRE issuing side (no approval without a funds/limit answer; structural). FAIL-OPEN but BOUNDED for the acquiring probabilistic fraud score (card and UPI pay-in): a fraud-rail circuit breaker separate from the Processor Port breaker (77), every fail-open transaction tagged and enqueued to the async risk/AML rail for post-hoc scoring and possible freeze/claw-back, and auto-escalation to fail-closed or a conservative rules-based stand-in when the breach rate crosses a threshold. Unsolicited-inbound (archetype 2) is async-only. A configurable posture mode (NORMAL vs LOCKDOWN) sets the effective posture as the STRICTER of {manual mode, auto-escalation state}; the posture flag is cached locally in the auth path and refreshed asynchronously, NEVER a synchronous per-transaction lookup; TIGHTENING is freely available to on-call, LOOSENING is a gated, more-privileged, audited, time-boxed override that must never silently disable the bounded-fail-open safeguards.
- **S10. Auth token and claims security (DESIGNED, Step 7 Decision 3).** Self-contained JWT access tokens verified LOCALLY (never a per-request auth/KMS lookup, T4), asymmetric ES256 with the private key in a multi-region KMS key and public keys via JWKS. LEAN tokens (role/permission-set reference resolved from asynchronously replicated, integrity-protected local config), IDs-ONLY claims (never PII or secrets; extends S7 to the auth surface), DISTINCT audiences per plane with mandatory iss/aud/typ/exp/nbf validation. RFC 8725 / OAuth 2.0 Security BCP hardening is MANDATORY (reject alg:none, pin the algorithm at every verifier, safe kid handling). Opaque rotating refresh tokens hashed at rest, one-time-use, family-wide revocation on reuse; the short access-TTL is the primary revocation bound; an any-principal-capable emergency denylist is the immediate-revocation path. The Auth service issues (off hot path) and reads identity/enrollment facts to resolve scope; it owns no identity (C1, C4).
- **S11. Service-to-service authentication and authorization (DESIGNED, Step 7 Decision 4a/4b/4d).** Workload identity is SPIFFE-style X.509-SVIDs with mTLS on synchronous calls and per-service Kafka principal authentication with broker ACLs on the async transport; verification is LOCAL on both (no central policy-decision-point, T4). EVERY S2S hop is authorized, never trusted by network location (zero-trust): the universal baseline is mesh-level default-deny authorization (coarse, caller-SVID-to-method), and Tier-1 resources (any whose compromise can cause, authorize, or expose money movement or money facts: the ledger posting path and query API, Money Movement intent and command intake, the fraud rail, Settlement intake) add rich resource-side authorization (operation plus scope) through a single `isAuthorized()` / `isWorkloadAuthorizedToPost()` abstraction reading a versioned, integrity-protected, SINGLE-SOURCE allowlist. Tiering is by DEPTH of check, not presence. The M4 posting grant is {posting SVID, allowed transaction-type set}, default-deny; TYPE IS STRUCTURALLY BOUND (the ledger rejects any posting whose account structure does not match its declared type's permitted account set, via ledger-owned templates or validation; type-scoping's blast-radius containment depends on this), and types are defined S2-AWARE (each segregated-pool movement is its own type, never a generic pooled type, so type-scoping enforces segregation, see M11). Async posting rides source-qualified topics `cmd.ledger.post.<holder>.v<n>` whose per-holder ACLs are CI-GENERATED FROM THE ALLOWLIST (single source, the decision-71 policy-as-code pattern); the mesh does authN and coarse reachability only and NEVER encodes the grant; the allowlist is the authoritative kill switch because the ledger re-checks type at consume time (removal is fail-closed under either deploy ordering). Read authorization on money facts mirrors this: sync via the query API's Tier-1 check, async via broker consumer ACLs generated single-source from a versioned consumer-allowlist (Kafka-ACL implementation swappable, decision 33 intact); reads are SCOPED by caller authorization, never blanket (decision 73 already closed PII on these topics, this controls economically sensitive data; account-scope expression in the query API is deferred to ledger-query-API design). The ledger transaction record immutably STAMPS the authenticated posting identity (caller SVID on sync, source-qualified topic owner on async) for provenance (amends decision 21 / Section 9, permanent under M2). Grants change only through reviewed versioned config plus CI, NEVER a runtime control plane; emergency removal is broker-ACL-pull plus mesh-deny plus SPIRE-deregister, made durable by config revert; an M4-grant change is a separation-of-duties change (dual control plus security sign-off, now locked as Decision 6c Tier 4 with an organizationally independent security approver). Every authorization DENY emits an alertable security audit event. The abstraction is contracted over an abstract `AuthenticatedCaller` and `PostingRequest`, hiding the resolution (allowlist today, verified capability claims or a policy engine later), so the upgrade is mechanical (O4-style isolation). Residual authorized-but-compromised-caller risk is bounded by the fraud rail, M8 recon, and M4 type-scoping, not by this layer.
- **S12. Transport identity-trust deployment invariant (Step 7 Decision 4a).** Where mTLS terminates at a sidecar, the application accepts the peer identity ONLY from its own sidecar over loopback, the sidecar STRIPS any client-supplied identity header (XFCC-style), and the application port is NOT directly reachable bypassing the sidecar; otherwise the peer identity is spoofable and "the resource is the authorization authority" (S11) has a bypass under it. The alternative is app-level mTLS with the SPIRE SVID terminated in-process (no sidecar in the auth decision). One or the other is MANDATORY for any Tier-1 resource. Consequence: SPIRE is availability-critical for the SYNC posting path (SVIDs age out if it is down, failing sync posts CLOSED, which is correct for money); the async path uses a separate Kafka credential and is unaffected. The 4a substrate (SPIRE, broker ACLs, the allowlist) is on the DR-region readiness checklist alongside the multi-region KMS key (decision 79).
- **S13. RLS-exempt workload role scoping and human access (DESIGNED, Step 7 Decision 4c; NARROWS decision 69 / chapter 07.B).** The RLS-exempt "platform role" is a CLASS of per-workload, per-table, least-privilege DB roles bound to workload SVIDs, default-deny under FORCE RLS with application roles never owning tables. WORKLOAD grant only. Exemption is reserved for irreducibly-cross-Program operations (recon matching, inbound settlement-file posting, platform-only tables); decomposable processing (payment orchestration, the outbound settlement cycle) runs under ENFORCED RLS iterating scope per Program. Internal HUMANS, including super-admin, hold least-privilege permission-set-and-scope by role, NEVER blanket access and never a standing RLS-exempt connection; the scope hierarchy (super-admin all-Programs, tenant its Programs, Program its own) is a CEILING on scope, not a grant floor. Broad or cross-Program human reach is delivered through curated services that hold the exempt role and enforce the human's authorization at the API boundary, and through the analytics warehouse for aggregates, never raw operational-DB access. On-demand human elevation is bounded, time-boxed with automatic expiry, justified, separately approved, and audited (issued/used/expired), widening only API-enforced scope, never raw DB reach; emergency direct-DB break-glass with RLS bypass is a SEPARATE gated, dual-controlled, statement-logged procedure (now locked as Decision 6c Tier 3 plus statement-logging, a vaulted single-use credential, and mandatory post-hoc review). Exemption and the SVID-to-role mapping are versioned, single-source, CODEOWNERS-gated, CI-deployed, no runtime control plane. Every exempt-role connection is logged; cross-Program access occurs only in identified audited operations; human-on-behalf operations log the human, service, and operation; unmapped attempts to assume an exempt role are alertable.
- **S14. External-principal credential handling (DESIGNED, Step 7 Decision 5).** Merchant API keys are AUTH-OWNED edge credentials with a record/secret split: the `api_` typed ID is the loggable record; the secret is a separate 256-bit show-once value (`apsk_live_`/`apsk_test_`, vendor-distinct prefix plus checksum for secret scanning), HMAC-SHA-256 hashed with a KMS/Secrets-Manager-custodied PEPPER at rest (password KDFs rejected on entropy arithmetic; no per-key salt; dual-pepper rotation with re-hash-on-verify), carried ONLY in the Authorization header, redacted at the edge BEFORE the first log write (failures included; logs carry the `api_` id plus display fingerprint). A key binds ONE merchant plus an EXPLICIT STATIC Program subset (validated at issuance and at resolution) plus ONE permission set; `api_keys:manage`, KYC attestation (K3), and posture/elevation controls are STRUCTURALLY outside the class-4 permission universe; live/test are separated planes enforced at resolution like an audience mismatch; on-behalf-of for merchant trees is a request parameter authorized against the hierarchy, never a multi-merchant credential. Rotation is N concurrent active keys with guided roll (immediate/1h/24h/3d/7d expiry on the old key); three revocation classes (scheduled expiry local; immediate revoke at projection-replication latency, seconds, alarmed; emergency kill via the Decision 3 any-principal denylist); revoked is a STATUS, records never deleted; no forced max-age by default with a Program-level policy hook; scope/permission WIDENING on a live key requires step-up (Decision 6) and bumps the key epoch. Resolution is LOCAL at the per-plane merchant-API edge against an async-replicated integrity-protected projection, ZERO per-request network calls, structurally FAIL-CLOSED for authentication with last-good-projection ride-through and the denylist as the independent kill channel; verification material travels ONLY on the ACL'd auth-config channel, never fact topics. The resolved AuthenticatedPrincipal context propagates under the TRUSTED-ASSERTER rule: only edge SVIDs on the 4d allowlist may assert an external-principal context, any other asserter is denied and alarmed; kept behind an O4-style seam with recorded flip triggers to edge token exchange. Idempotency scope derives from the RESOLVED principal, never a request-body field. HARD TYPE SEPARATION from S11: no external credential ever authenticates an internal hop, no internal workload ever holds an external credential (no internal service-account API keys, ever), and posting capability is UNREPRESENTABLE for an external principal (the M4 grant subject is a workload SVID); provenance is two-layer (ledger stamps the workload; the merchant principal rides intent/attempt records and envelopes).

- **S15. Operational and administrative permissions (DESIGNED, Step 7 Decision 6, sub-items 6a to 6e; the Decision-6 validation reconciliation is RATIFIED and folded in, context 16.7).** Human authentication assurance is a THREE-LEVEL ladder (NIST 800-63B aligned: AAL1 unused for privileged access, AAL2 the human floor, AAL3 hardware phishing-resistant for the highest-blast-radius internal roles), carried as `acr`/`amr` enum claims in the D3 token (IDs/enums only, S10.5, read locally, T4). Phishing-resistant factors (FIDO2/WebAuthn) preferred, TOTP acceptable, SMS OTP fallback-only and never primary. MFA is MANDATORY for internal humans (class 3, AAL2 floor, no opt-out), MANDATORY AAL3 for super-admin, posture-control holders (S9), and 6c dual-control approvers; STRONGLY RECOMMENDED for class 2 (Program-flag-mandatory) and class 1 (mandatory for admins and any step-up-capable principal); NOT APPLICABLE to machine/service principals (classes 4/5, assurance is the credential, 5f). SESSIONS apply to classes 1/2/3 only (the D3 refresh-token family) with two independent bounds, IDLE and ABSOLUTE (absolute forces full re-auth including MFA), enforced at the refresh call off the hot path; kill is D3 family revocation plus the denylist. ## 3. Known traps and anti-patterns (these recur, stay vigilant)

- **T1.** "Everything talks to everything" / "all products communicate efficiently." The single most likely thing to wreck the design, and the instinct that resurfaces repeatedly. Efficiency comes from products _not_ calling each other. Catch it every time. Violates C1/C2.
- **T2.** Treating a product as the canonical owner of a shared entity (e.g. TMS "owning" the merchant or the transaction). The merchant is owned once by Identity; money by the Ledger. Products hold projections and references only.
- **T3.** Modeling a relationship as an entity type (e.g. "bank vs direct" as a merchant attribute). It is a Program/enrollment property. See I5.
- **T4.** Central chokepoints: a gateway that decodes every ID type, a central ID service, a central event publisher, a god orchestrator coordinating every saga. All rejected. Codec, outbox, ID generation, and orchestration are per-service / per-flow, never central.
- **T5.** Over-decomposition: splitting one domain with many surfaces into many services (the acceptance surfaces). One domain equals one context.
- **T6.** Chasing exactly-once delivery, or assuming ordered delivery without a consumer-side state check. See E2/E5.
- **T7.** Copying source-of-truth state (KYC status, identity, balances) into a local table as a mutable copy instead of a projection updated by events. Drift equals incident.
- **T8.** Designing a product's internals before confirming it touches the platform only through the allowed rail contracts. New products integrate with rails, never with each other.
- **T9.** Choreographing a money flow (no single owner of saga state), or smearing saga state into business tables, or chasing a distributed transaction across services for effectively-once. All three make the flow unauditable or un-swappable or both. See O1/O4/E6.
- **T10.** Privileging one settlement model (cards) as "the template" and bolting other rails onto card-shaped abstractions. The reusable base is the four archetypes as parameterisations of a generic PaymentIntent spine, never a card flow with extensions. Stripe's documented mistake: "global payment methods aren't different, cards are." See chapter 04.
- **T11.** Binding to a named payment processor instead of the Processor Port (blocks the future switch swap, C6), or assuming the internal MSK bus's guarantees (per-aggregate ordering, replay) apply to the external developer-facing webhook delivery rail (DESIGNED, rule S17: weaker guarantees, no ordering promise, at-least-once, signed; per-aggregate ordering stays internal per E5 and is never extended across the network boundary).
- **T12.** Putting workflow state in the ledger (availability buckets, freeze buckets, in-flight buckets), or enforcing an operational control in two places (a freeze posted in the ledger AND checked in the settlement engine). The ledger records economic truth; the owning context owns workflow state; one owner per fact. Dual enforcement drifts. This is the hybrid-proposal lesson (chapter 06.D2) and the reason Payout In-Transit was replaced (chapter 06.B).
- **T13.** Scale mechanics silently weakening Tier-1 claims: a time-partitioned unique constraint is unique-per-period, not a permanent floor (M7, decision 74); a single hot synchronous balance row under row locks melts at capture TPS (decision 75). Any partitioning, sharding, or caching change touching the ledger re-runs the M7/M10 claims before it ships.
- **T14.** Treating the AI model as a trust or authorization boundary: letting the LLM decide what it may read, execute, or act as, or treating prompt injection as merely a "read confidential data" risk. The model is never the authority; enforcement is always at the data or command boundary under the session principal (S24, D97), and the AI's entire context (prompts, retrieved documents, tool outputs) is untrusted input (S8). Equally: minting a broad cross-domain "AI principal" that can act across fraud, settlement, support, and merchant domains, the god-principal the architecture decomposes away from; autonomy belongs in the owning domain or a purpose-scoped process-manager service under least privilege (S24, D2, S13).

## 5. New-component design gate (run before adding ANY product or service)

A checklist. Every "no" is a stop, fix it or escalate.

1. **Layer.** Which layer (0/1/2) or which rail is it? Does it depend only downward? (C1)
2. **Calls.** Does it avoid calling any sibling product? (C2)
3. **Identity.** Does it reference `merchant_id`/`customer_id` and hold a projection, not its own copy of identity/KYC? (I1, K2)
4. **Money.** If it moves money: does it post only via the ledger API under a granted, TYPE-SCOPED capability (an M4 allowlist entry {posting SVID, allowed transaction-type set}), with its own outbox, and does it respect Program-decides-postings? Is each declared type structurally bound to its permitted account set, is every segregated-pool movement a distinct S2-aware type held by exactly ONE holder (M11), and does the ledger stamp the authenticated poster onto the record? (M4, M5, M11, E1, S11)
5. **Events.** Events-as-facts, versioned schema, standard envelope, correct partition key by ordering boundary, idempotent consumers? (E1 to E5, C5)
6. **Data.** Owns its own data, no cross-context reads? (C4)
7. **Enrollment.** Does it slot into `merchant × Program × product`, with config on the enrollment? (architure_context.md Section 7)
8. **Security.** Card data tokenized/vaulted, no raw PAN on the bus, PII minimized, funds not co-mingled, residency honored, no PII on money topics, inbound notifications authenticated? (S1 to S8)
9. **Confidence.** Does it depend on a DEFAULT decision (Section 4) that this product now stresses enough to justify reopening?
10. **Idempotency.** If it mutates money: does every money-mutating endpoint require an idempotency key, with downstream keys deterministically derived from the stable trigger, and the ledger unique constraint as the floor? Same-key-different-payload rejected, in-flight retry guarded? (M7) Do all keys follow the canonical grammar (chapter 06.A)?
11. **Orchestration.** If it runs a multi-step money flow: is the flow orchestrated by a single owning context (not choreographed, not central)? Short saga vs long process-manager chosen correctly? Compensation defined per step as a forward reversing posting? Saga state in an isolated, swappable layer? (O1 to O4)
12. **Effectively-once.** Is each consumer effect independently idempotent (ledger key for money, inbox for local non-ledger effects), with no attempt at a cross-service transaction? (E6)
13. **Archetype.** Which money-flow archetype does it map to, or which composition (split-settlement, load, withdrawal)? Does each leg follow that archetype's state machine, compensation, and keys? (chapter 04) If it is issuing-side (network calls us), it maps to the parked issuing family (chapter 06.E) and cannot ship before that fork is decided.
14. **Processor.** Does every external payment execution go through the Processor Port, never a named processor, so a future switch swap is free? (C6)
15. **Indeterminate state.** For any externally indeterminate outcome, does it resolve by reconciliation, never assumption? (M8)
16. **Intent/attempt state.** Is intent-level state separated from attempt-level state (retryable intent, terminal attempts)? (O5)
17. **Isolation.** Are its tenant-visible rows program_id-scoped in the correct table class, enforced by claims plus application predicates plus RLS, with internal processing under the platform role deliberately? (chapter 07)
18. **Scale mechanics.** Floors respected on funds accounts, no synchronous balance row on unfloored aggregates, unique floors preserved under any partitioning, bounded retention plus owner backfill honored? (M10, M7, E9, T13)
19. **Auth and risk posture.** Does it declare its principal classes and the claims/permissions it needs (context Section 16.1-16.2)? Are its tokens IDs-only with per-plane audiences and RFC 8725 hardening (S10)? Does it have a SPIFFE workload identity, and is EVERY S2S hop it adds authorized (mesh default-deny baseline; and if it is a Tier-1 money-adjacent resource, i.e. its compromise can cause, authorize, or expose money movement or money facts, rich resource-side operation-plus-scope authz through the shared abstraction reading the single-source allowlist), with the S12 transport-identity-trust deployment invariant satisfied? Are any money-fact reads it performs SCOPED, not blanket? (S11, S12) If it connects directly to a Program-scoped DB, does it run under ENFORCED RLS unless it is irreducibly cross-Program, and only then under a per-workload least-privilege RLS-exempt role, with no standing human grant? (S13) Does any auth path it adds honor the fraud-rail posture (S9): fail-closed for solvency and issuing, fail-open-bounded for the acquiring fraud score, the posture flag locally cached and never looked up per request? If it exposes a merchant-facing API surface, does it sit behind the merchant-API edge and class-4 resolution per S14, never its own credential scheme?
20. **Operational and admin auth (S15).** If it exposes human-operable admin or sensitive operations: do its human principals carry the right MFA assurance (AAL2 floor, AAL3 for super-admin, posture-control, and dual-control-approver roles), with idle AND absolute session timeouts and step-up (min-`acr` plus `auth_time` freshness) at its high-risk operations? Do its privileged actions map to the correct control tier (single-actor step-up, elevated-and-time-boxed, dual-control, or dual-control-plus-security-sign-off), with grant/widen/loosen gated but kill/tighten/remove always free? If it has a merchant-API edge, are brute-force (source-throttled, never credential-locked, never keyed on the loggable `api_` id), per-key/per-merchant token-bucket quotas (429 plus retry-after), and auth-endpoint rate limiting present, all fail-open-on-their-own-failure and OUTSIDE the S9 fraud posture? Does every sensitive authorization decision and every DENY emit an IDs-only record to the append-only tamper-evident India-only audit store via the outbox (never a synchronous hot-path write), with compliance-driven retention and legal-hold overriding erasure? If it sits behind the external ingress edge, do its 6d application-layer controls compose with a separate network layer as three orthogonal dimensions (Shield-class L3/L4 volume, WAF L7 shape plus coarse per-source shedding, 6d per-principal fairness), with per-principal quota owned ONLY by 6d and never the WAF (T12), the WAF coarse limit set above the max legitimate single-principal rate so principal overage is adjudicated by the 6d 429 not masked by an opaque WAF block, and the layers on independent failure domains so the WAF/Shield layer backstops a 6d fail-open window (Decision 110, Section 17)? (S15)
21. **Sandbox / test-mode (S16).** If it handles merchant-facing money or data: does it honor the live/test `mode` boundary, with test money routing to the SEPARATE test ledger and its own topics (never a `mode` column on shared ledger tables), and mode-tagging above the money plane per chapter-07 isolation? Does it read `mode` from the AUTHENTICATED claim, never a request-body field? Does it keep real recon (M8), settlement, and fraud UNWIRED from test? If it executes payments, does it go through the C6 Processor Port so the test simulator substitutes cleanly, and does any reset it performs hard-drop only the separate test ledger while epoch-bumping (never DELETE-ing) shared live tables? (S16, context 16.8)
22. **External webhook delivery (S17).** If it emits merchant-facing events or adds any merchant-facing outbound event surface: does it deliver ONLY through the external webhook rail, never a bespoke outbound-event scheme, so the T11 posture and the decision-80 separate-versioned-contract boundary hold? Is every new merchant-facing event a curated `resource.event` type in domain vocabulary (81a), rendered as a rail-composed projection (86a) carrying IDs, economic fields, and only entitled merchant-appropriate fields, never the internal fact passed through, never raw PAN or CVV (S1), never cross-party PII (86c), with PII confined to the external artifact while internal money and transactional topics stay IDs-only (S7)? Does it leave endpoint ownership and lifecycle, per-endpoint HMAC signing with re-sign-per-attempt (83), event-type-plus-Program-scope filtering with no content filter (84b), and durable process-manager delivery with bounded backoff-plus-jitter retry, no ordering, and auto-disable (85) to the rail, with any redelivery reusing the `evt_` and re-signing a fresh timestamp? Is webhook-URL mutation a class-1 human step-up operation and never a class-4 key capability (82b, 6a)? Are the rail's stores, projections, and delivery logs India-resident with secrets and signatures redacted before the first log line (S6, 5c)?

23. **Notification delivery (S18).** If it emits merchant-facing or end-customer notifications, or adds any notification surface: does it deliver ONLY through the notification rail, never a bespoke outbound-message scheme (C5, O1, T11)? Does every notification type carry a MANDATORY-or-OPTIONAL class (90), mandatory un-silenceable and skipping the resolver, optional suppressible at (consumer, product/Program, type, channel) resolved at send with no rail-held preference state? Is end-customer notification product-scoped and default-OFF, enabled per product by deliberate override, with concrete regulated end-customer flows (UPI e-mandate pre-debit, RBI card transaction alerts) specified WITH their product and never speculatively (87)? Is recipient contact RESOLVED at send from the owning context or a compacted-identity projection, never a money topic, with the rail holding no standing contact copy, no-contact a first-class skip and source-unavailable retriable (88, S7)? Is preference state owned by the shared Consumer Preferences context keyed (consumer, product/Program, type, channel), written through with no local product copy and no identity/KYC (91, T7, I1/K2)? Do channels sit behind the swappable provider port (89, C6) with the build-vs-SaaS engine deferred, and are delivery and channel feedback normalized to a bounded outcome set with the two suppression kinds (deliverability all-class vs consent optional-only) never conflated (94)? Is the message a rail-composed projection with raw PAN/CVV/track never present (S1), templates versioned and mandatory-class templates CODEOWNERS-gated (93)? For SMS, does it own the DLT template-ID/header/category binding as template attributes keeping the port swappable, with regulatory category distinct from the mandatory/optional class and the promotional-scrubbing pipeline deferred (95, India-only)? Is any latency-sensitive code (OTP) sent on the priority lane as an ephemeral, never-persisted, never-logged payload (92, S4)? Do mandatory-class regulated notices write a dispatch-evidence record with a rendered-content hash, IDs-only, compliance-retained with legal-hold overriding erasure (96)? Are the rail's stores, projections, and logs India-resident with contact and content redacted before the first log line (S6, 5c)?

24. **Analytics/reporting delivery (S19).** If it exposes analytical or reporting reads, or adds any query surface over cross-context data: does it read ONLY through the analytics rail's mediation layer, never a direct warehouse or operational-DB connection, with scope re-derived from token claims and caller-supplied scope ignored (decision 99, S13)? Does it consume facts via its own consumer group, never a cross-context DB read or a producer dual-write (C4, decision 29)? Are its tenant-visible rows program_id-carried, identity IDs-only in the raw and internal layers, aggregates per-Program-decomposable with no irreversible pre-aggregation (decision 97)? Does PII enter ONLY at ingest from the owning context or a compacted-identity projection, never off a money topic, resident (86a/88, S6, S7)? Does every result carry a freshness watermark, and is any authoritative or regulatory output generated from or tie-out-reconciled against the system of record, never a bare warehouse number (decision 100)? Does PII erasure physically delete where the store is mutable and crypto-shred where a copy survives, under per-subject-destroyable keys with deterministic re-derivation, statutory retention and legal holds overriding (decision 101, decision 73)? Is it READ-ONLY-consumed, with any action routed through the owning product's authorized command path, never through analytics (decision 97)? Is decision 69 relationship-gating honored on the tenant read path, and is internal cross-tenant analytics a mediated audited capability, never a standing raw grant (decision 99, S13)?

25. **Fulfillment provisioning and shipping (S20).** If it provisions, personalizes, ships, or tracks a physical device or collateral, or adds any such surface: does it go through the Fulfillment rail, never a bespoke vendor integration (C5, O1)? Are Units born at procurement intake with physical, inventory, and shipping facts Fulfillment-owned, the active device-to-merchant binding and activation left to TMS (decision 63), the QR value left to Acceptance/TMS (transmitted not minted, T2), and device-to-tenant derived via Program never a device attribute (I5, T3)? Are the two inbound vendor channels file-shaped and S8-untrusted behind the C6 Fulfillment port under the authenticated class-6 vendor principal, integrity and schema verified with file-level plus per-Unit idempotency (E6, no M7 floor), partial-file discrepancy quarantine (06.D4 posture), and the intake sheet the only Unit-creating channel? Are outbound artifacts a minimized need-to-print-and-ship projection with shipping-recipient PII entitled per-adapter by function, raw PAN/CVV never leaving the vault (S1, T10), never an internal fact or KYC record, S6-resident and IDs-only logged (S5, S7, 86a)? 29. **AI / model / agent surface (S24).** If it embeds an LLM or a model-driven decision, or exposes an AI, natural-language, or agent surface: is the model NEVER the authorization authority, with every read enforced at the query boundary and every action at the command boundary under the SESSION PRINCIPAL (analytics via the S19 mediation, D97; actions only through the owning product's authorized command path via a curated boundary-authorized tool surface, never a raw internal API, the D80/D86 pattern)?
